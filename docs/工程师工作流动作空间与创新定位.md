# 工程师工作流动作空间：与 CadQuery / COMAct 路线的差异及创新定位

> 撰写日期：2026-09-28  
> 对应前文：`docs/项目分析与通用化改进及LLM评测方案.md` §2.1–2.2  
> 本文单独展开「为什么 CAD 难」「化繁为简该聚什么」以及如何避免与既有工作雷同。

---

## 0. 一句话主张

把 CAD 自动化的难点重新表述为**动作空间的抽象问题**：不让大模型直接写 CadQuery 脚本，也不让它裸调 SolidWorks COM；而是模拟机械工程师分阶段的设计流程，把繁琐 API 聚合成**工程语义级的 workflow 工具**，并从执行轨迹中自动归纳、验证、演化这套工具库。最终产出原生、可编辑、带设计意图的 SolidWorks 模型。

---

## 1. 问题从哪里来

上一份报告把当前系统的失败归纳为：LLM 必须直接输出米制坐标、射线选面、语义边名；草图没有预检；高层特征缺失；机构接口按产品定制。这些现象指向同一个根因：

**CAD 难以被大模型攻克，主要不是因为模型不懂零件长什么样，而是因为原生 API 太碎、引用太难、专业门槛太高。**

机械工程师不会说「从 (0.015, 0, 0.02) 向 (0, −1, 0) 射一条射线，选中第 3 个面，再画 4 条线」。他们说的是：

> 先定骨架和关键尺寸，再做基体，再按孔向导打安装孔，圆角放最后，然后测量、查干涉。

因此，改进方向不应是「再找一种更容易生成的几何语言」，而应是 **把 SolidWorks 的繁琐 API 按工程师真正的工作方式聚合起来**。

这一判断本身是对的。但若只停在「把多个 API 包成更简洁的接口」，创新点站不住：审稿人会说这就是一套封装得更好的 API。本文后面要回答的是：**聚合什么、怎么得到这些聚合、凭什么能泛化、和已有工作差在哪里。**

---

## 2. 必须避开的三条已有路线

| 路线 | 代表 | 核心做法 | 容易被说成的雷同点 |
|---|---|---|---|
| 程序化 CAD | CAD-Recode、Text2CAD、各类 CadQuery / build123d 生成 | LLM 输出几何脚本，OCC 等内核求值 | 动作空间是 Python DSL，不是原生 CAD 流程 |
| 固定高层 API | SimpleCADAPI 一类 | 人手把常用调用收成更短的函数表 | 抽象停在「操作级」，库是静态的 |
| 直接操作 COM | COMAct | Agent / Claude Code 通过 COM 调 SolidWorks 原子接口 | 动作空间仍是繁琐 API，只是执行器换成了 agent |

本仓库如果沿用「生成 CadQuery 中间程序再编译回 SolidWorks」，会立刻落入第一条。如果开放原子 COM 让外部 coding agent 自己摸索，会落入第三条。当前项目里已经出现的反例是第三条的变体再叠上第二条的误用：伞、行星轮系、缝纫机各自有一套解析求解器——每来一类产品就新写一个接口，抽象滑到了**产品模板层**，不能泛化。

目标动作空间必须同时满足：

1. 输出是 **原生特征树**（孔向导、方程式、配合、Toolbox），而不是一段 OCC 脚本。
2. 接口是 **工程语义**（面名、骨架引用、标准件规格），而不是射线和米制对角点。
3. 工具库可以 **从轨迹中学习并验证**，而不是一次性手写死。
4. 流程是 **分阶段门控**，而不是扁平的一篮子函数。

---

## 3. 核心想法：模拟工程师的 workflow，而不是模拟 API 调用

### 3.1 操作层聚合不够

把「选面 + 画圆 + 切除」收成 `cut_hole(cx, cy, r)`，只减少了调用次数，没有降低专业门槛。工程师真正重复的是**带设计意图的阶段**，不是单条特征。

建议把一次建模拆成固定阶段，每个阶段只开放该阶段需要的工具，并配上该阶段的检查：

| 阶段 | 工程师在做什么 | 开放的工具类型 | 阶段门禁（机器可验） |
|---|---|---|---|
| Spec | 明确关键尺寸、功能面、未指定项 | 提问、写参数表、标记假设 | 参数表完整；歧义已记录或已提问 |
| Skeleton | Top-down 骨架 / 主草图 | 基准面、轴、关键尺寸、布局草图 | 关键尺寸可测；后续特征能引用这些名字 |
| Base | 基体特征 | 拉伸 / 旋转 / 扫掠等主体 | 单实体；包围盒与主尺寸对齐 |
| Secondary | 孔、槽、凸台、筋 | 孔向导、阵列、镜像、抽壳 | 孔位相对骨架；功能孔数量与规格满足 |
| Detail | 圆角、倒角、外观 | 边选择器 + 圆角/倒角 | 仍是有效实体；底面等功能面未被破坏 |
| Check | 测量、干涉、壁厚、DFM | `measure`、干涉、剖面 | 硬需求全部通过，才能结束 |

这和「给 LLM 一大堆扁平 API 让它自己挑」有本质区别：每一步的决策空间被阶段裁剪了，工程惯例（圆角放最后、先骨架后细节）写进了控制流，而不是只写在 prompt 里。

### 3.2 引用必须是工程语义，不是几何坐标

SolidWorks API 繁琐的核心不在调用次数，而在**选中哪个拓扑实体**。圆角或开孔之后，射线和「top_front」这类方盒边名就会失效。

工具层应接受工程师词汇，例如：

```
hole_wizard(
  face="base.top",
  pattern="rect 2x2",
  offset_from=["edge.left=15mm", "edge.front=15mm"],
  spec="M5 CSK"
)
```

由工具层维护持久命名（特征创建时登记 `base.top`、`H1`、`skeleton.axis_A`），在当前 B-rep 上解析选择器，再调用孔向导和 Toolbox。算术（`base_len/2 - 15`）由参数表和方程式完成，不由 LLM 心算毫米再除以 1000。

CadQuery 路线很难占这条：它没有孔向导、标准件库、配合求解和可在 SolidWorks 里按习惯改的特征树。

### 3.3 抽象必须停在「一类几何 / 一类工程动作」，不能停在「一类产品」

| 过低 | 合适 | 过高（本仓库已踩过） |
|---|---|---|
| `sketch_line` + 射线选面 | `hole_wizard`、`shell`、`mate_concentric` | `assembly_set_radial_deployable_pose`（伞专用） |
| 逐点渐开线 | `gear(module, z, pa, …)` | `make_sewing_machine` |

原则与现有 generalization 规则一致：**一个工具对应一类可迁移能力，不对应一个评测物体。**

## 4. 真正的研究增量：workflow 库是学出来的，不是手写完的

如果全部 workflow 都由作者手工设计，论文仍容易被说成「又一个静态高层 API」。建议把聚合做成可观测的学习过程。

### 4.1 从轨迹挖掘候选工具

数据来源可以并行使用，但评测类别不得参与工具设计：

- Agent 在原子或操作级 API 上**成功**的轨迹；
- 工程师录制的 SolidWorks 宏；
- 公开 CAD 数据集里的特征历史（仅用于发现共现模式，不把答案写进运行时）。

挖出高频、语义一致的调用子序列，由 LLM 提议一个带参数的新工具：名字和参数用工程师词汇，内部展开成现有 C# 端点。

### 4.2 验证后才入库

新工具必须同时满足：

1. 在回归集上执行成功；
2. 在 **held-out** 任务上降低步数或失败率，或提高严格通过率；
3. 接口不绑定具体 case 名、图片哈希或产品名。

不再降低这些指标的工具要降级或淘汰。覆盖不到的几何允许回退到原子 API，并统计「工具库覆盖率随迭代如何增长」。

### 4.3 这件事和已有路线的差别

- 相对 SimpleCADAPI：库不是发布时冻住的函数表，而是有准入、淘汰和覆盖率曲线的。
- 相对 CadQuery 生成：学到的是 **SolidWorks 工程动作**（孔向导、配合、骨架引用），不是 OCC 脚本惯用法。
- 相对 COMAct：模型默认看不到原子 COM；只有工具缺失时才短暂降级，降级轨迹再回流到挖掘管线。

程序合成里类似思想叫 library learning。把它用在**商业 CAD 的原生 API + 工程师阶段门控**上，需要投稿前再做一次文献检索确认空白；但即便有相近工作，差异仍应落在「原生可编辑模型 + 阶段门控 + 工程语义引用」这三点上，而不是「又学了一批宏」。

---

## 5. 输出必须是可编辑的设计，而不只是对的实体

CadQuery 脚本对工程师的交付物不友好：改一个尺寸往往要改代码再重跑。本路线的交付物应是：

- `.SLDPRT` / `.SLDASM`，特征树可读；
- 尺寸进入方程式 / 全局变量，和 Spec 参数表绑定；
- 孔是孔向导特征，标准件来自 Toolbox，装配靠配合而不是写死坐标。

因此评测必须增加 **可编辑性 / 局部性**：在完成的模型上追加一句「底板加长 20mm」，检查再生是否成功、未改动区域的几何是否保持。这个指标是 CadQuery 生成和裸 COM 轨迹都不自然具备的，也是「模拟工程师」主张的直接证据。

---

## 6. 用实验把「抽象层级」变成自变量

核心论点是「API 太繁琐，需要化繁为简」。最有说服力的实验是：同一批任务、同一组模型，只改动作空间。

| 档位 | 动作空间 | 对照对象 |
|---|---|---|
| L0 | 原子 COM / 当前 `OperationType` | COMAct 风格 |
| L1 | 固定手写操作级 API（Shell/Hole/Mirror…） | SimpleCADAPI 风格 |
| L2 | 生成 CadQuery 再求值（可选对照，不作为本系统主路径） | 程序化 CAD 文献 |
| L3 | 手工阶段门控 + 工程语义工具，库不进化 | 本文的「静态 workflow」消融 |
| L4 | L3 + 从开发集轨迹自动挖掘并验证入库 | 完整方案 |

报告指标：

- 质量：严格通过率、pass@k、需求满足率、IoU（见评测方案报告 §3）；
- 过程：步数、token、修复轮数、工具覆盖率、回退到原子 API 的比例；
- 泛化：在**未见零件类别**上的通过率；
- 可编辑性：修改指令后的再生成功与局部 IoU；
- 模型规模：若 7B–30B 在 L3/L4 上接近大模型在 L0 上的表现，就能直接支持「降低 API 门槛」这一主张。

L2 只作为外部对照，避免系统主路径变成 CadQuery 生成器。

---

## 7. 装配与机构：主场，而不是零件的附录

只做零件时，和 CadQuery 路线的差距会被缩小。SolidWorks 原生路线的不可替代处在：

1. **配合定位**：LLM 写「轴 A 与孔 B 同心、端面贴合」，求解器给位姿，不再把坐标写进 prompt。
2. **标准件与孔规格**：M5 沉头、轴承、齿轮用 Toolbox / 生成器，而不是点云齿廓。
3. **骨架驱动的装配**：零件尺寸引用骨架，改中心距则零件和配合一起再生。
4. **通用运动学图**：用关节类型 + 数值求解（或 mate / Motion Study）替换「一种产品一个 C# 求解器」。

现有台灯 / 伞 / 电钻 / 缝纫机接口应视为 **L4 挖掘之前的负例**：它们证明「按产品聚合」不可扩展，而不是本方案要保留的终点。

---

## 8. 风险与约束

1. **抽象层级滑向产品模板**。一旦工具名或参数里出现评测物体，就违反 generalization 规则，也毁了创新叙事。准入检查必须拒收这类候选。
2. **测试集污染**。workflow 只能从 public / 开发轨迹学习；隐藏测试集和论文主表 case 不得参与工具设计。
3. **阶段门控过死**。真实工程师有时会回退改骨架。允许带理由的阶段回退，但回退次数计入过程指标，防止模型把整个零件推倒重来。
4. **学习到的工具过拟合共现、没有因果**。验证集必须包含「同样特征、不同布局」的 held-out，避免把「骰子六点」收成专用工具。
5. **实现成本**。持久命名、孔向导、方程式、配合求解都要在 C# 端补齐；没有这些，工程语义只是 prompt 修辞。

## 9. 和上一份报告的关系

上一份报告 §2.2 建议引入参数化 CAD 中间语言，并列了 CadQuery DSL 与自定义 JSON IR。本文把优先级改成：

- **主路径**：工程师阶段门控 + 工程语义工具 + 可选的库学习；IR 是工具内部的参数表和命名拓扑，不是给 LLM 写的 CadQuery 程序。
- **仍值得保留的工程能力**（与路线无关）：表达式参数、草图离线预检、`export-step`、按 Spec 验收、标准化错误码、OCC 仅用于**评测几何**而不是作为建模前端。
- **明确降级**：不以「LLM 生成 CadQuery」或「LLM 直接打 COM」作为系统卖点。

评测协议（隐藏 GT、严格通过率、harness 分档、infra 与模型失败分离）仍然适用；本路线额外要求评测器能区分 L0–L4，并单独报告可编辑性。

## 10. 落地顺序（服从创新叙事，而不是先堆特征）

| 阶段 | 做什么 | 为了证明什么 |
|---|---|---|
| W0 | 参数表 + 持久命名 + 草图预检 + 错误码；补 Hole/Shell/Mirror 三个操作级工具 | 先证明「引用和阶段」比再堆原子 API 更能消失败 |
| W1 | 实现阶段门控 Agent：每阶段只注入该阶段工具和门禁 | 静态 workflow（L3）相对 L0/L1 的消融 |
| W2 | 装配改为配合 + 骨架，去掉评测 prompt 里的坐标泄露 | 原生 CAD 主场可测 |
| W3 | 轨迹挖掘 → 验证 → 入库；画覆盖率曲线 | 库学习相对手工 L3 的增量 |
| W4 | 可编辑性评测 + 小模型 vs 大模型 | 「化繁为简」对门槛和成本的主张 |

W0 里的 Hole/Shell/Mirror 是**一类几何的操作级工具**，用来给阶段门控垫底座，不是终点。不要在 W0 就写伞或缝纫机专用接口。

---

## 11. 结论

「模拟机械工程师、把繁琐 API 聚合成简洁 workflow」可以作为本项目相对 CadQuery 生成和 COMAct 的差异化，但创新不能落在「接口更短」四个字上。必须同时成立三件事：

1. **阶段**是工程师的阶段，不是函数列表的分组；
2. **参数**是工程语义和设计意图，不是坐标和射线；
3. **工具库**有学习、验证和淘汰，并且在未见类别上可测。

做到这三点，系统才是在降低 CAD 的专业门槛，而不是再实现一个几何 DSL 或再包一层 COM。
